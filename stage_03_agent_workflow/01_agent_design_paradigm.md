# Agent设计范式：从ReAct到工作流编排

> 对应周次：Week 1（本阶段） ｜ 投入：8小时 ｜ 前置：Stage 2完成

---

## 本文档目标

建立Agent的正确认知：Agent不是"更聪明的聊天机器人"，而是"**被工程约束框住的大模型决策单元**"。理解ReAct为什么被生产环境淘汰，工作流编排为什么成为主流。

---

## Step 1: Agent的本质拆解（1小时）

```
Agent = LLM(决策) + Tools(手脚) + State(记忆) + Orchestration(流程控制)

对比：
普通RAG:  问题 → 检索 → 生成（固定3步，无决策）
Agent:    问题 → LLM决定调什么工具 → 执行 → 看结果 → LLM决定下一步 → ...
```

LLM在Agent里只该干三件事：
1. **理解自然语言**（把口语转成结构化参数）
2. **做受限选择**（在给定的N个工具/分支里选）
3. **综合信息生成回复**

**它不该干**：自由决定流程、自行决定何时停止、发明不存在的工具。

## Step 2: ReAct的死穴（2小时）

### 2.1 复现ReAct的问题（用伪代码跑一遍）

```python
# ReAct循环：LLM自己决定一切
while True:
    thought = llm("你应该继续行动还是给出最终答案？当前状态:...")
    if "final answer" in thought:
        return thought
    tool = llm("你要调用哪个工具？")
    result = execute(tool)
    # ↑ 循环何时结束？只有LLM说了算
```

### 2.2 生产环境四大死穴（每个都要能举例）

| 死穴 | 具体表现 | 数学 |
|------|---------|------|
| **成功率连乘衰减** | 5步流程每步90% → 0.9⁵=59% | 业务根本不敢上 |
| **死循环** | "我再查一次" × 20 | Token烧钱，用户干等 |
| **不可预测** | 同样输入两次执行路径不同 | 无法测试、无法审计 |
| **排查地狱** | 出错时不知道它为什么走了这条路 | 日志一片混乱 |

**面试标准句**：*"ReAct把'流程控制权'交给了概率模型，而生产系统要求确定性。现代做法是把编排权还给代码，LLM只做节点内的局部决策。"*

## Step 3: 工作流编排范式（2小时）

```
        ┌────────── 代码画好的图（LangGraph） ──────────┐
        │                                               │
START ─►│ [改写] ─► [检索] ─► [路由] ─┬─► [工具A] ─► [校验] ─► END
        │                            └─► [工具B] ┘   │
        │                        (LLM在受限选项里选)   └─不合格→回到生成
        └───────────────────────────────────────────────┘
```

三种控制流对比：

| 控制方式 | 谁决定 | 适用 | 例子 |
|---------|--------|------|------|
| **固定链** | 代码 | 流程唯一 | 改写→检索→生成 |
| **分支路由** | LLM在N个枚举里选 | 分类明确 | 按问题类型分工具 |
| **循环重试** | 代码条件 | 质量不达标 | 校验失败重生成（限次数） |

**关键设计原则**：
1. LLM的每个"决策点"都是**选择题**（枚举），不是**问答题**（自由发挥）
2. 循环必须有**代码层面的硬上限**（max_iterations）
3. 每个节点的输入输出都是**强类型**（State）

## Step 4: Agent vs RAG的关系（1小时）

不是替代，是**包含**。Stage 2做的RAG在Agent里长这样：

```
[检索节点] = HybridRetriever（直接复用Stage 2的类！）
[改写节点] = QueryRewriter（直接复用！）
[生成节点] = 带引用生成（直接复用！）
```

Agent新增的是：**路由、工具调用、校验循环、跨步骤状态**。所以Stage 3不是推倒重来，是给RAG装上决策骨架。
